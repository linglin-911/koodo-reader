## 1. 项目目标

基于 Koodo Reader 现有桌面阅读器，改造成更适合长篇网络小说阅读、素材收集和剧情研究的阅读工具。

核心目标：

1. 能够流畅打开、阅读约 **100MB 以内**的大型 TXT 小说。
2. 保留 Koodo 原有书库和阅读体验，尤其是文字选择、复制、选择后的操作菜单、笔记创建入口及编辑区域。
3. 在 Koodo 原有笔记/高亮能力基础上，逐步实现三种适合小说研究的批注：小批注、章节批注、大批注。
4. 批注能准确关联原文或章节，并能在原文与批注之间快速定位。
5. 尽量复用 Koodo 原有功能和数据，不破坏用户已经导入的小说、阅读记录、笔记和高亮。

### 1.1 数据与使用方式的关键决定

- 小说仍然导入并保存在 **Koodo 原有书库**中，继续使用 Koodo 的书籍管理和阅读入口。
- **不采用旧 FujiyNotepad 项目的独立小说项目文件夹方案**；当前不为每本小说另建 `novel.txt`、`project.json` 和独立 SQLite 数据库。
- 需要兼容并保留当前 Koodo 安装版已有的小说和笔记数据。
- 当前开发版与原安装版已经验证会读取同一份用户数据。开发和测试时必须注意数据安全，避免同时运行两个版本造成写入冲突；不得为了测试而清空或重建用户数据库。
- 项目以个人使用为主，同时保留后续开源的可能性。

## 3. 大型 TXT 阅读性能

### 3.1 目标与现状

目标是让约 100MB 以内的 TXT 小说能够稳定、流畅地打开和连续阅读。

已知用户实测现象：

- 官方 Koodo v2.4.6 打开约 70MB TXT 时存在明显卡顿。
- 官方版本在笔记/高亮操作中曾出现闪退。
- 原生文字选择、复制、选择后的菜单定位、菜单创建笔记和笔记编辑区的交互体验基本符合预期，应尽量保留。
- 后续测试中，用户曾观察到一次滚动较顺畅、另一次明显卡顿；滚动性能并非每次测试都以相同程度复现。
- 用户另一次实测中，切换到滚动模式后曾卡顿数分钟但未崩溃；进程内存约 2GB，随后稳定在约 1.8GB，关闭阅读器后约降至 300MB。该数值属于用户观察，不等同于单份日志的内存采样。
- 章节边界处存在独立的连续滚动问题：向下滚动到当前章节末尾后继续滚轮，会有一段输入没有带动正文移动；等待下一章加载并切换完成后才恢复响应。向上滚动到章节开头时也有相同现象。
- 上述现象的所有根因尚未完全确认；本节区分日志已证实的数据、代码调用链和待验证推测。

### 3.2 性能验收需要记录的指标

后续以真实大文件进行基准测试，至少记录：

- 文件大小、编码、总行数、字符数和章节数。
- 导入/打开耗时、首次正文可见耗时。
- findCurrentLine、章节索引构建、章节 HTML 生成、DOM 解析、章节挂载和阅读位置恢复的分段耗时。
- 延迟任务是否再次解析全书，以及重复解析的次数和总耗时。
- 当前 iframe / Document 中的章节数量、正文 DOM 节点数量、章节 HTML 缓存数量。
- 打开后主进程与渲染进程内存；连续滚动时内存是否持续增长。
- 连续滚动的帧率/长帧、滚轮输入到画面响应的延迟、章节边界处丢失或积压的滚轮输入。
- 章节目录快速滚动、远距离跳转和重新打开目录时是否回跳。
- 文字选择、复制、菜单弹出是否正常。
- 笔记/高亮创建、编辑、定位和恢复的数据库读取、IPC、数据处理、DOM 绘制分段耗时。
- 关闭书籍或窗口后 DOM、Blob URL、缓存和内存是否合理释放。

测试应至少覆盖用户此前遇到问题的约 70MB 文件，并逐步增加到接近 100MB 的文件。测试结果要保留日志和可复现步骤；小说正文不得写入日志或提交 Git。

### 3.3 静态分析发现的风险（尚未全部由日志确认）

此前静态分析提出过以下潜在瓶颈，尚不能全部当作已确认根因：

- 全文读取到 ArrayBuffer 后一次性解码。
- 使用 split("\n") 创建过大的行数组。
- 一次性拼接大量 HTML。
- 使用 DOMParser 对整本书或大量章节进行解析。
- 多个章节的 HTML 同时常驻内存。
- 延迟触发的 refreshContent() 可能再次进行大范围解析。
- Blob URL 在书籍卸载时未充分释放。
- Rangy/TreeWalker、splitText() 和 span 包裹等高亮逻辑可能增加大 DOM 的操作成本。

其中，延迟 refreshContent() 的全书解析已经由后续日志确认；其他项目仍需分别验证，不能把静态风险直接写成已确认根因。

### 3.4 2026-11-07 大型 TXT 日志诊断结果

以下数据来自用户本地约 70MB 小说的诊断日志。日志只用于分析，没有将小说或日志文件提交到仓库。

**测试样本：**

- 文件大小：76,083,283 bytes，约 72.6 MiB。
- 编码：UTF-8。
- 解码后字符数：25,885,051。
- 行数：382,034。
- 完整解析后章节索引：约 7,702 章，chapterDocCount 为 7,703。

**A. 首次加载与 large-file-window 路径**

- 一次从较靠后的阅读位置打开时，findCurrentLine 定位到第 318,468 行，耗时 1,727.6ms。
- 同次 txtToHtml 耗时 1,810.9ms；DOM 解析耗时 12.6ms；章节 HTML 拆分耗时 157.2ms；章节索引构建耗时 187.8ms；renderTo 总耗时 2,276.2ms。
- 该次初始渲染报告 chapterDocCount=6,896。后续全文件刷新则报告 chapterDocCount=7,703。两者统计口径/索引范围是否一致尚未确认，必须在后续设计中查清，不能直接假定初始章节索引完整。
- 另一次定位到第 57,769 行时，findCurrentLine 耗时 294ms，初始 renderTo 耗时 538.2ms，goToPosition 耗时 678.4ms；另一次相近位置测试的 findCurrentLine 耗时 392.6ms，初始 renderTo 耗时 651.5ms。
- 日志显示 findCurrentLine 耗时会随目标行位置明显变化：靠前位置可低于 1ms，较深位置达到数百毫秒，最深一次达到 1,727.6ms。这提示当前定位可能存在从头扫描的成本，需要检查实际实现并改为可快速定位的行偏移/索引结构；在检查代码前不把具体算法认定为已确认。

**B. 首屏之后再次触发的全文件解析（已确认的主要问题）**

初始加载使用 large-file-window 后，日志仍在稍后触发 delayedTxtRefresh，并以 refresh=true 再次走全文件解析。该路径记录为 conversionMode=full-file，没有继续沿用首次加载的窗口范围。

- 再次生成的 HTML 达到 28,392,899 个字符，htmlParts=382,034。
- DOM 解析阶段的 bodyChildCount=382,034，即 body 下直接子节点数量，不代表整个 Document 的总 DOM 节点数。
- 全文件 HTML 转换约 1.5–1.8 秒。
- DOM 解析约 324–356ms。
- 章节 HTML 拆分约 603–687ms。
- refreshContent / delayedTxtRefresh 总耗时约 2.57–2.80 秒；同一大文件的多次日志均出现这一全文件刷新。
- 这意味着即使用户已经看到初始正文，稍后仍可能发生一次全书级解码/HTML/DOM/章节拆分工作，抵消 large-file-window 首次加载的收益，并可能造成随后一段时间的卡顿和额外内存占用。

**结论：** 应优先确认 delayedTxtRefresh 的用途和调用条件。若它只是为了补齐章节信息，应改为补齐轻量章节索引或局部窗口数据，不得再次把全书转换为约 2,839 万字符 HTML 并创建 38 万级 body 子节点。若确实需要刷新，必须证明其必要性，并避免与首次加载重复处理同一份正文。

**C. 章节 HTML 加载的偶发长耗时**

- 大多数 loadChapterHtml 记录约 1–3ms。
- 同一组日志也出现过 3,759.1ms、1,126.7ms、1,105.6ms、1,154.3ms、1,081.3ms 等异常长耗时。
- 因此不能只依据通常 1–3ms 的记录判断章节加载始终很快。需要进一步拆分章节文本获取、Blob URL 创建、iframe/document 写入、CSS 处理、布局和高度计算，确认长耗时发生在哪一段，以及是否与全文件刷新或内存压力重合。

**D. 批注恢复中的数据库读取异常**

- 一次仅有 6 条笔记的恢复记录，dbReadDurationMs=96,658.3ms，而 renderDurationMs 仅 0.6ms。
- 同一测试过程中，后续数据库读取还出现约 4,107ms、1,231ms、1,344ms 的记录；其他测试也出现约 1,705ms、4,126ms，以及约 4.7 秒的读取。
- 这说明当时的主要耗时并不在已记录的高亮 DOM 绘制阶段；异常集中在日志标记为 dbRead 的阶段。
- 目前还不能断定一定是 SQLite SQL 本身慢，也可能涉及 database-command IPC 排队、主进程任务阻塞、重复查询、数据序列化/传输或计时范围问题。下一步必须将 IPC 往返、SQL 执行、结果读取/序列化和 Renderer 后续处理分别计时。
- 不能因为未来批注可能达到几千或上万条，就先把全部完整批注正文永久放入内存；也不能用缓存掩盖当前仅 6 条笔记就出现的异常读取延迟。

**E. 阅读位置恢复计时异常**

- 一次 goToPosition 的日志开始时间与结束时间相差约 97 秒，但该函数自身记录的 durationMs 只有 1,334.4ms。
- 同一 trace 的批注数据库读取又记录了约 96.7 秒。两组时间高度异常，但目前不能直接认定它们是同一个阻塞点。
- 必须检查计时器起止范围、异步调用链、IPC 等待、多个阅读器实例/重复打开和主线程阻塞，解释墙钟时间与函数内部耗时为何不一致。

**F. 内存采样**

- 一次成功采样记录的渲染进程 workingSetSize 约 1,439,744KB（约 1.37GiB），peakWorkingSetSize 约 1,754,540KB（约 1.67GiB），privateBytes 约 1,371,228KB（约 1.31GiB）。
- 早期诊断日志曾因 webContents.getProcessMemoryInfo is not a function 导致采样失败；后续日志已经出现有效的 Renderer 内存采样。后续仍需保证采样接口与当前 Electron 版本匹配。
- 这些采样说明大文件阅读过程的资源占用较高，但单个采样点不能证明存在内存泄漏。必须比较打开、首屏、延迟刷新、连续滚动、切换章节、关闭书籍后的内存变化。

### 3.5 当前诊断结论与处理优先级

根据现有日志和代码检查，当前优先级如下：

1. **最高优先级：消除首屏之后的全文件重复解析。** delayedTxtRefresh 从 large-file-window 切换到 full-file 已有日志证据，是目前最明确、影响范围最大的性能问题。
2. **高优先级：优化深位置定位。** findCurrentLine 在深位置达到 1.7 秒，需检查是否逐行扫描，并建立可直接定位的行偏移/章节索引，避免每次从文件开头重新搜索。
3. **高优先级：查明数据库读取和 IPC 异常。** 6 条笔记出现 96.7 秒读取时间，不能归因于批注数量或高亮绘制；必须拆分 SQL 与 IPC 耗时。
4. **高优先级：定位章节加载的偶发长耗时。** 不能只优化平均值，应追踪 1–4 秒级异常样本。
5. **高优先级：建立连续章节渲染窗口。** 解决章节边界处清空正文、等待下一章加载造成的空滑和断层。
6. **持续关注：控制 DOM、HTML、Blob URL 和缓存的生命周期。** 以实际内存曲线验证，不根据单次内存值贸然重写。
7. **暂不把“批注全部缓存”作为性能优化的第一步。** 先解决日志已暴露的数据库读取异常，再按批注数据量设计有界缓存。

当前日志没有对章节边界滚轮输入、滚动帧耗时和滚轮事件是否被丢弃进行完整埋点。因此，章节边界断层的代码路径已经找到，但其每一段实际耗时仍需专门测量。

### 3.6 滚动模式连续章节窗口方案（待设计确认、尚未实现）

**目标：** 滚动模式下，用户从当前章节滚动到上一章/下一章时，正文应像一篇连续长文一样自然衔接，不再出现章节末尾/开头空滑等待。该方案先针对 TXT 的 readerMode=scroll 实施；EPUB、PDF、漫画和分页模式不随意改动。

**当前代码调用链已确认：**

- Koodo src/utils/reader/mouseEvent.ts 的 bindHtmlEvent() 处理滚轮事件。普通滚动路径会先 sleep(200)，然后执行 rendition.record()，再通过 scrollChapter() 检查是否到达章节顶部/底部。
- scrollChapter() 在边界处调用 rendition.prev() / rendition.next()；当前机制是在滚到边界后才触发章节切换，没有提前把下一章正文放入当前滚动流。
- Kookit src/utils/navigationUtil.ts 的 handleRenderChapter() 会清空当前 doc.body.innerHTML、把 iframe 高度设为 0、重置滚动位置，再读取并挂载目标章节正文，随后处理 CSS、iframe 高度和滚动位置。
- 因此当前滚动模式在章节边界处并不是把下一章接到已有正文后面，而是清空当前 iframe document 的正文，再异步生成和挂载下一章。这个机制与用户观察到的边界断层高度吻合。
- src/renders/GeneralRender.ts 中每 3 秒检查底部的定时器属于自动滚动功能，不是普通手动滚轮边界断层的直接触发路径；排查时不要把两者混为一谈。

**建议目标架构：一个 iframe / Document 承载多个相邻章节容器，而不是每章创建一个 iframe。**

示意结构：

    <div data-chapter-index="99">第99章正文</div>
    <div data-chapter-index="100">第100章正文</div>
    <div data-chapter-index="101">第101章正文</div>

具体要求：

1. 保留一个滚动容器和一个 iframe Document，在其正文中同时挂载当前章节及前后少量章节的独立容器。
2. 当前章节尚未到达底部时，就提前读取并渲染下一章；向上阅读时也提前准备上一章。跨越边界时直接滚入已存在的相邻章节，不再清空整个 body 后等待重新挂载。
3. 使用有界章节窗口：DOM 只保留当前视口附近和少量前后缓冲章节；不允许把 7,000 多章全部渲染进 DOM。
4. 章节离开窗口时，释放远离视口的正文 DOM；必要时用占位容器保留已测量的高度，并保存稳定的阅读锚点，避免回收章节后 scrollTop 和视口位置突然跳动。重新向回滚动时再按需恢复章节。
5. 章节元数据与章节正文彻底分离。章节索引只保存目录和定位必需的轻量信息，例如章节 ID、序号、标题、原文起止位置/偏移；不能为了显示目录而生成全书 HTML 或挂载全书正文 DOM。
6. 章节窗口管理器根据当前可视章节、滚动方向和距离提前加载相邻章节；若用户快速跨越多个短章节，应连续补齐窗口，不能每次只等一个章节加载完再继续。
7. 阅读进度记录必须根据当前可视章节容器确定章节 ID/序号及章节内偏移，不能继续假定整个 iframe body 只属于一个章节。
8. 对普通滚动改用滚动位置监测和 requestAnimationFrame 合并处理；接近边界时提前预加载。阅读进度记录采用节流/防抖，不要每次滚轮事件都先固定等待 200ms 再检查边界。
9. 章节边界不能吞掉用户的滚轮输入。下一章尚未准备好时，应保留待处理的滚动距离，或在章节挂载后补偿滚动；目标是用户连续滚轮时不需要停下来重新滚一次。
10. 继续复用现有文字选择、复制、链接、笔记/高亮能力；多章节共存时，事件监听应避免随章节重复绑定，批注定位必须能区分章节容器。
11. 该方案是目标架构，尚未实现或验收。需要先做 TXT 滚动模式最小原型，再决定章节窗口大小、预加载阈值、占位高度缓存和资源回收策略。

### 3.7 批注缓存与章节目录的资源策略（待实施）

**批注缓存：**

- 可考虑把轻量批注索引常驻内存：批注 ID、类型、分类、所属章节、短摘要、时间、原文锚点位置等。
- 按类型、分类、章节建立内存索引；跨章节批注应能映射到关联章节。
- 批注完整正文、长摘录和其他附加数据在打开详情时再读取，不要在多个缓存结构中重复保存完整对象。
- 新建、编辑、删除后同步更新索引；切换书籍时释放上一部书的缓存。
- 几千到一万条轻量元数据可作为待测目标，但不能在没有内存测量的情况下承诺固定上限；必须测试长摘要、多个锚点和跨章节映射带来的对象开销。
- 只为当前章节/可视区域附近的批注生成正文高亮 DOM；不要因为批注索引在内存中，就把全书所有批注标记一次性渲染到 DOM。
- 先查明 dbReadDurationMs 异常的根因，再决定哪些查询需要缓存；不能用全量缓存掩盖 IPC 或数据库阻塞。

**章节目录：**

- 章节目录渲染只包含章节标题、编号、展开状态和必要的定位元数据，不包含章节正文。
- 章节索引可以保存全书的轻量章节元数据；目录 UI 只渲染当前可见区域及少量上下缓冲行，采用虚拟列表，避免一次创建数千个目录 DOM 节点。
- 用户从第 1 章快速滚动到第 500 章，应通过目录索引和虚拟列表直接定位，不应逐章加载正文，也不应等待 1–499 章正文渲染。
- 目录滚动性能仍需用 7,000+ 章节样本实测，特别验证快速滚动、远距离跳转、展开/折叠和当前章节定位。
- 目录列表虚拟化与正文章节窗口是两套不同机制：前者只管理目录行 DOM，后者管理阅读区正文 DOM，不得混为一谈。

### 3.8 优化验收要求

完成相关优化后，至少验证：

- 约 70MB、约 38 万行、约 7,700 章 TXT 打开时不再在首屏显示后重复生成全书 HTML/DOM。
- 从第 1 章、约第 1,600 章和约第 6,800 章打开时，定位耗时不会随目标位置线性增长到秒级。
- 连续向下/向上滚动跨越章节边界时，不出现可感知空滑；快速连续滚轮可以自然跨越多个章节。
- 章节窗口的 DOM 数量有明确上限，向前/向后滚动时内存不会随阅读章节数持续增长。
- 目录从第 1 章快速滚动到第 500 章及更远位置时不回跳、不加载正文，并能保持交互响应。
- 批注数量分别为少量、约 1,000 条和约 10,000 条时，数据库查询、索引缓存、详情读取和可视区高亮渲染均有分段耗时记录。
- 原生文字选择、复制、选择菜单、笔记编辑、章节跳转、阅读位置保存/恢复和已有书库数据兼容不退化。
- 记录测试设备、文件大小、章节数、内存、滚轮响应和长帧；未实测的平台或场景必须明确标记待测。

优化过程中必须保留原生选区、复制、菜单和笔记入口，不能为了性能而直接破坏这些交互。

## 4. 三类小说研究批注

三类批注是本项目需要建立的小说研究能力。它们是不同粒度的独立实体，不能简单做成一条批注的父子层级。

### 4.1 小批注

用途：记录具体原文中的剧情细节、人物行为、伏笔、设定、精彩片段等。

需求：

- 一条小批注可以关联多个原文片段。
- 一条小批注的多个关联片段可以位于不同章节。
- **单个原文锚点必须完整位于一个章节内**，不能让单个锚点跨越章节边界。
- 不同小批注可以关联同一段原文；锚点允许交叠、嵌套。
- 支持分类、内容管理和原文定位。
- 从原文选中内容创建小批注时，尽量复用 Koodo 原生选择、菜单和笔记编辑流程。
- 后续应支持将新的原文片段追加到已有小批注，而不是只能重复创建新批注。

原文定位要求：

- 锚点必须基于文本内容/文本位置，而不是屏幕像素坐标。
- 锚点不能因为字体、字号、窗口尺寸或行距变化而改变含义。
- 优先研究并复用 Koodo 当前文本内容与 DOM 之间已有的定位机制。
- 若需要持久化偏移量，应统一字符偏移口径，并处理中文、补充字符及 LF/CRLF 换行；具体数据结构必须先检查 Koodo 现有实现再确定。
- 原文变化后的锚点失效检测和重新匹配策略，需在实现前单独设计。

### 4.2 章节批注

用途：对单个章节进行概括、评价和分析。

需求：

- 一条章节批注只绑定一个具体章节。
- 同一个章节允许存在多条章节批注。
- 不需要绑定章节中的具体文字区间。
- 应能从阅读器当前所在章节创建章节批注；创建时应根据鼠标/阅读位置识别章节，不应强制用户先精确选中文字。
- 支持独立分类、创建、编辑、删除、搜索/筛选和跳转到对应章节。

### 4.3 大批注

用途：整理连续多个章节的阶段剧情总结，以及人物成长线、人物关系、感情线、势力变化、伏笔回收和世界观变化等。

需求：

- 一条大批注可以关联多个章节；沿用此前设计时，默认以连续章节范围作为主要使用方式。
- 大批注有自己的正文、分类和管理能力。
- 大批注与小批注、章节批注相互独立，不建立自动父子关系。
- 大批注可以按章节查询并展示相关小批注、章节批注作为参考资料，但这些参考资料不是大批注的子记录。
- 修改或删除一条小批注/章节批注，不应自动修改或删除大批注正文；反之亦然。
- 大批注后续可采用独立写作工作区；此前设计为参考资料区 + 正文编辑区的分栏形式。当前 Koodo Fork 中的具体 UI 需要结合原生界面重新设计，不得直接认定旧项目界面已经移植完成。

### 4.4 三类批注之间的关系

| 类型 | 绑定对象 | 是否独立 | 主要作用 |
|---|---|---|---|
| 小批注 | 一个或多个原文锚点 | 是 | 收集具体素材 |
| 章节批注 | 一个章节 | 是 | 分析单章 |
| 大批注 | 多个章节 | 是 | 阶段总结和专题分析 |

三类批注各自拥有自己的内容、分类和管理方式。它们之间可以按章节互相查阅参考，但不自动从属、不因一方修改或删除而连带改变另一方。

### 4.5 与 Koodo 原生笔记/高亮的关系（待设计）

- 现有 Koodo 原生笔记和高亮必须保留，不能直接清空、覆盖或通过重建数据库来替代。
- 用户认可 Koodo 原生文字选择、菜单定位和笔记编辑流程，优先在此基础上轻量改造交互。
- 新三类批注的底层数据需要重新设计，但必须先检查现有 Koodo 笔记/高亮数据模型、数据库表和 IPC 数据流。
- 尚未最终决定：原生 Note 与新小批注之间采用扩展、映射还是并存方式。必须先给出兼容方案，再实施数据库改动。
- 不允许未经确认就执行破坏性迁移或更改已有数据含义。

## 5. 阅读体验与界面要求

已明确的方向：

- 以长篇小说连续阅读为核心，不要把软件重新做成通用文本编辑器。
- 尽量保留 Koodo 原生阅读器、书库和操作习惯。
- 章节标题需要居中显示，字号明显大于正文，形成清晰的章节视觉层级。
- 笔记弹窗以轻量调整为主，避免为了三类批注而完全推翻用户已经认可的原生选区和笔记创建流程。
- 批注在原文中的视觉提示应兼顾可读性，不应让标记大面积遮挡正文；具体采用何种标记形式，需结合 Koodo 原生高亮机制和实际效果再确定。

### 5.1 章节目录浏览与章节跳转

目录打开期间由用户控制；阅读位置变化、章节加载完成或笔记操作不得擅自改变用户正在浏览的目录位置。

**当前已实现并由用户验证通过：**

- 目录打开期间，用户可以自由滚动；阅读章节变化不会自动带动目录滚动。
- 点击目录章节后，红色加粗标识立即更新；正文跳转及章节加载完成后，目录不会滚回被点击章节。
- 每次重新打开目录时，读取当前书籍的 recordLocation，展开包含当前章节的父级目录路径，并将当前章节滚动到目录可见区域中间。
- 重新展开当前章节父级路径时，保留用户此前展开的其他目录分支。
- 章节目录/页码通过 chapter-pages 事件更新，并在阅读引擎实例更换或组件卸载时解除监听。
- 保留独立的「返回原处」机制：目录跳转前保存阅读位置，点击返回按钮恢复跳转前位置。

**已发现、后续需要优化的细节：**

- 左侧目录面板目前通过 CSS transform 隐藏，NavigationPanel / ContentList 仍保持挂载；因此目录滚动容器的 DOM scrollTop 会自然保留上次手动浏览的位置，并非另有一份目录位置存储。
- 重新打开时，代码会调用 scrollContents(..., true, "center")，而 scrollContents() 使用 behavior: "smooth"。所以界面会从上次保留的位置平滑滚动到当前章节。
- 用户希望后续改为：关闭目录后不保留上次滚动位置；重新打开时直接定位（不播放从旧位置滚动过来的动画），当前章节处于可见区域中间，并尽可能同时显示其上下相邻章节。
- **目录滚轮回跳问题：已解决。** 此前曾出现只滚动约两次时目录自动回到当前阅读章节附近、连续滚动超过三次则通常不回跳的现象；用户已确认该问题解决。该问题保留为历史记录，不再作为待排查事项或后续开发任务。
- 章节目录应使用轻量章节元数据和虚拟列表：全书标题索引可以预先建立，但只把可视区域及少量缓冲行挂载为 DOM。目录滚动到第 500 章不应加载第 1–499 章正文；该性能仍需实测。

目录跳转与「返回原处」应继续相互独立；后续调整目录滚动时，不得破坏阅读位置恢复功能。目录列表虚拟化也不得与正文章节窗口混为一谈。


## 6. 当前技术架构与开发约束

当前仓库的架构（依据仓库 `AGENTS.md`）：

| 层 | 主要位置 | 职责 |
|---|---|---|
| Electron 主进程 | `main.js` | 窗口、IPC、SQLite（better-sqlite3）、原生集成 |

| Kookit 阅读引擎 | `kookit` 独立源码仓库；Koodo 中使用构建产物 | 书籍解析、阅读相关工具 |
| Go HTTP 服务 | `httpserver/` | 可选 KOReader / OPDS 集成 |

开发时必须遵守：

1. 代码修改前先阅读当前仓库的 `AGENTS.md`，并检查 GitHub/本地当前分支的真实代码，不得依赖旧对话猜测实现。
2. 涉及代码编写、修改或 Review 前，先读取 `AGENTS.md` 和仓库内的 `.agents/skills/karpathy-guidelines/SKILL.md`；如果当前 Agent 的全局技能列表未提供该技能，直接读取仓库文件，不得因此阻塞开发。
3. 先搜索现有实现并复用，不做无必要的大规模重构。
4. 所有数据库操作必须通过 `database-command` IPC；渲染进程不得直接操作 SQLite。
5. 不得读取 `src/assets/lib/` 下的混淆/压缩产物来理解源码，包括 `kookit-extra.min.mjs`、`kookit.min.js`、`kookit-extra-browser.min.js`；需要研究阅读引擎时，应查看 Kookit 源码仓库。
6. Zustand 使用 `src/store/useAppStore.ts`，组件使用字段级 selector，不新增旧 Redux/connect 模式。
7. 用户可见文本使用 react-i18next，不硬编码界面文案。
8. 高频 `mousemove` / `scroll` / `resize` 事件必须按仓库规范节流。
9. 保护现有书库、笔记、高亮和阅读数据；数据库结构调整前先说明迁移与回滚策略。
10. 遵循当前仓库 `AGENTS.md`：用户已委托 Agent 负责开发时，完成修改、检查差异及适用验证后，应主动提交到当前工作分支；不得 force push、重写历史或推送到主分支。
11. 每个相对独立的功能完成后，执行类型检查、构建和针对性测试；不反复验收已通过的功能。

下一步工作：

- 使用用户此前遇到卡顿问题的约 70MB TXT，检查第一阶段诊断日志是否正常、完整。

## 10. 下一阶段开发顺序

当前阶段以大型 TXT 性能和连续滚动为首要任务，按以下顺序推进：

1. **确认并处理延迟全文件重解析。** 检查 delayedTxtRefresh / refreshContent() 的调用目的、触发条件和数据依赖；优先避免首屏已经显示后再次把全书转换为 HTML、DOM 和完整章节 HTML。若只需补充章节信息，应改为构建轻量章节索引或补充局部窗口数据。
2. **优化深位置章节定位。** 检查 findCurrentLine 是否从头扫描；根据真实代码选择行偏移索引、二分查找或其他可随机定位的数据结构。验证第 1 章、第 1,600 章和第 6,800 章附近的定位时间。
3. **拆分批注数据库读取和 IPC 耗时。** 将 dbReadDurationMs 拆为 IPC 往返、SQL 执行、结果读取/序列化和 Renderer 处理；解释 6 条笔记出现约 96.7 秒读取时间的原因。不要先把所有完整批注正文缓存进内存。
4. **定位章节 HTML 加载偶发长耗时。** 针对 1–4 秒级 loadChapterHtml 样本补充细分计时，确认章节内容生成、Blob、iframe 写入、CSS、布局和高度计算中真正耗时的阶段。
5. **实现 TXT 滚动模式连续章节窗口。** 先做最小原型：一个 iframe Document 同时承载当前章及前后少量章节容器；提前预加载相邻章节；使用有界 DOM 窗口和占位高度保持滚动位置；章节边界不再清空整个 body 后等待新章加载。先只作用于 TXT 滚动模式，其他格式维持原有路径。
6. **优化滚动事件和阅读进度记录。** 检查 mouseEvent.ts 中固定 sleep(200)、边界检查和事件锁；改为滚动位置监测、requestAnimationFrame 合并、预加载和节流记录。确保章节切换前后的滚轮输入不会丢失。
7. **按需评估章节目录虚拟列表。** 保持章节元数据可直接索引，只渲染可视目录行；以 7,000+ 章节样本验证远距离滚动、跳转、展开/折叠的响应和 DOM 数量。目录滚轮回跳已解决，不应重复排查或回归为未解决问题。
8. **做有界缓存与压力测试。** 先验证正文 DOM、HTML/Blob、布局和批注索引的资源上限，再测试约 1,000 / 10,000 条批注；批注完整正文按需读取，可视区附近才创建高亮 DOM。
9. 每项优化后执行类型检查、构建和针对性回归，重点保护连续滚动、文字选择、复制、菜单、笔记/高亮和已有书库数据。
10. 性能基线和主要瓶颈处理稳定后，再推进三类批注的数据兼容设计与完整实现。

不要重复要求用户验收已经通过的开发环境和双向数据互通；除非后续改动触及相关模块。不要在日志证据尚未解释前一次性重写整个阅读引擎。
