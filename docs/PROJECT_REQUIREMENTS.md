## 1. 项目目标

基于 Koodo Reader 现有桌面阅读器，改造成更适合长篇网络小说阅读、素材收集和剧情研究的阅读工具。

核心目标：

1. 能够流畅打开、阅读约 **100MB 以内**的大型 TXT 小说。
2. 保留 Koodo 原有书库和阅读体验，尤其是文字选择、复制、选择后的操作菜单、笔记创建入口及编辑区域。
3. 在 Koodo 原有笔记/高亮能力基础上，逐步实现三种适合小说研究的批注：小批注、章节批注、大批注。
4. 批注能准确关联原文或章节，并能在原文与批注之间快速定位。
5. 尽量复用 Koodo 原有功能和数据，不破坏用户已经导入的小说、阅读记录、笔记和高亮。

### 1.1 数据与使用方式的关键决定

- 小说仍然导入并保存在 **Koodo 原有书库**中，继续使用 Koodo 的书籍管理和阅读入口。
- **不采用旧 FujiyNotepad 项目的独立小说项目文件夹方案**；当前不为每本小说另建 `novel.txt`、`project.json` 和独立 SQLite 数据库。
- 需要兼容并保留当前 Koodo 安装版已有的小说和笔记数据。
- 当前开发版与原安装版已经验证会读取同一份用户数据。开发和测试时必须注意数据安全，避免同时运行两个版本造成写入冲突；不得为了测试而清空或重建用户数据库。
- 项目以个人使用为主，同时保留后续开源的可能性。

## 3. 大型 TXT 阅读性能

### 3.1 目标与现状

目标是让约 100MB 以内的 TXT 小说能够稳定、流畅地打开和连续阅读。

已知用户实测现象：

- 官方 Koodo v2.4.6 打开约 70MB TXT 时存在明显卡顿。
- 官方版本在笔记/高亮操作中曾出现闪退。
- 原生文字选择、复制、选择后的菜单定位、菜单创建笔记和笔记编辑区的交互体验基本符合预期，应尽量保留。
- 上述卡顿和闪退的最终根因尚未确认；不能仅凭现象认定是某一个模块造成的。

### 3.2 性能验收需要记录的指标

后续以真实大文件进行基准测试，至少记录：

- 文件大小、编码、总行数。
- 导入/打开耗时。
- 首次正文可见耗时。
- 章节目录生成耗时。
- 打开后主进程与渲染进程内存。
- 连续滚动时是否掉帧、卡顿或长时间无响应。
- 文字选择、复制、菜单弹出是否正常。
- 笔记/高亮创建、编辑、定位是否稳定。
- 关闭书籍或窗口后内存是否合理释放。

测试应至少覆盖用户此前遇到问题的约 70MB 文件，并逐步增加到接近 100MB 的文件。测试结果要保留日志和可复现步骤。

### 3.3 已识别的性能风险（目前属于待验证假设）

此前静态分析提出过以下潜在瓶颈，尚不能当作已确认根因：

- 全文读取到 ArrayBuffer 后一次性解码。
- 使用 `split("\\n")` 创建过大的行数组。
- 一次性拼接大量 HTML。
- 使用 DOMParser 对整本书或大量章节进行解析。
- 多个章节的 HTML 同时常驻内存。
- 延迟触发的 `refreshContent()` 可能再次进行大范围解析。
- Blob URL 在书籍卸载时未充分释放。
- Rangy/TreeWalker、`splitText()` 和 span 包裹等高亮逻辑可能增加大 DOM 的操作成本。

下一步必须通过日志、性能采样和逐项实验确认瓶颈，不要在未经验证的情况下大规模重写阅读器。

### 3.4 建议实施顺序

1. 完成诊断日志和基准数据采集。
2. 确认文件读取、解码、行索引和章节内容生成的真实开销。
3. 根据实测结果实施分块/流式读取、按需生成内容或有界缓存等优化。
4. 检查 Blob URL、DOM、章节缓存和其他资源的生命周期。
5. 单独验证高亮、笔记等 DOM 操作对大文件的影响。
6. 性能稳定后，再推进三类小说研究批注的完整实现。

优化过程中必须保留原生选区、复制、菜单和笔记入口，不能为了性能而直接破坏这些交互。

## 4. 三类小说研究批注

三类批注是本项目需要建立的小说研究能力。它们是不同粒度的独立实体，不能简单做成一条批注的父子层级。

### 4.1 小批注

用途：记录具体原文中的剧情细节、人物行为、伏笔、设定、精彩片段等。

需求：

- 一条小批注可以关联多个原文片段。
- 一条小批注的多个关联片段可以位于不同章节。
- **单个原文锚点必须完整位于一个章节内**，不能让单个锚点跨越章节边界。
- 不同小批注可以关联同一段原文；锚点允许交叠、嵌套。
- 支持分类、内容管理和原文定位。
- 从原文选中内容创建小批注时，尽量复用 Koodo 原生选择、菜单和笔记编辑流程。
- 后续应支持将新的原文片段追加到已有小批注，而不是只能重复创建新批注。

原文定位要求：

- 锚点必须基于文本内容/文本位置，而不是屏幕像素坐标。
- 锚点不能因为字体、字号、窗口尺寸或行距变化而改变含义。
- 优先研究并复用 Koodo 当前文本内容与 DOM 之间已有的定位机制。
- 若需要持久化偏移量，应统一字符偏移口径，并处理中文、补充字符及 LF/CRLF 换行；具体数据结构必须先检查 Koodo 现有实现再确定。
- 原文变化后的锚点失效检测和重新匹配策略，需在实现前单独设计。

### 4.2 章节批注

用途：对单个章节进行概括、评价和分析。

需求：

- 一条章节批注只绑定一个具体章节。
- 同一个章节允许存在多条章节批注。
- 不需要绑定章节中的具体文字区间。
- 应能从阅读器当前所在章节创建章节批注；创建时应根据鼠标/阅读位置识别章节，不应强制用户先精确选中文字。
- 支持独立分类、创建、编辑、删除、搜索/筛选和跳转到对应章节。

### 4.3 大批注

用途：整理连续多个章节的阶段剧情总结，以及人物成长线、人物关系、感情线、势力变化、伏笔回收和世界观变化等。

需求：

- 一条大批注可以关联多个章节；沿用此前设计时，默认以连续章节范围作为主要使用方式。
- 大批注有自己的正文、分类和管理能力。
- 大批注与小批注、章节批注相互独立，不建立自动父子关系。
- 大批注可以按章节查询并展示相关小批注、章节批注作为参考资料，但这些参考资料不是大批注的子记录。
- 修改或删除一条小批注/章节批注，不应自动修改或删除大批注正文；反之亦然。
- 大批注后续可采用独立写作工作区；此前设计为参考资料区 + 正文编辑区的分栏形式。当前 Koodo Fork 中的具体 UI 需要结合原生界面重新设计，不得直接认定旧项目界面已经移植完成。

### 4.4 三类批注之间的关系

| 类型 | 绑定对象 | 是否独立 | 主要作用 |
|---|---|---|---|
| 小批注 | 一个或多个原文锚点 | 是 | 收集具体素材 |
| 章节批注 | 一个章节 | 是 | 分析单章 |
| 大批注 | 多个章节 | 是 | 阶段总结和专题分析 |

三类批注各自拥有自己的内容、分类和管理方式。它们之间可以按章节互相查阅参考，但不自动从属、不因一方修改或删除而连带改变另一方。

### 4.5 与 Koodo 原生笔记/高亮的关系（待设计）

- 现有 Koodo 原生笔记和高亮必须保留，不能直接清空、覆盖或通过重建数据库来替代。
- 用户认可 Koodo 原生文字选择、菜单定位和笔记编辑流程，优先在此基础上轻量改造交互。
- 新三类批注的底层数据需要重新设计，但必须先检查现有 Koodo 笔记/高亮数据模型、数据库表和 IPC 数据流。
- 尚未最终决定：原生 Note 与新小批注之间采用扩展、映射还是并存方式。必须先给出兼容方案，再实施数据库改动。
- 不允许未经确认就执行破坏性迁移或更改已有数据含义。

## 5. 阅读体验与界面要求

已明确的方向：

- 以长篇小说连续阅读为核心，不要把软件重新做成通用文本编辑器。
- 尽量保留 Koodo 原生阅读器、书库和操作习惯。
- 章节标题需要居中显示，字号明显大于正文，形成清晰的章节视觉层级。
- 笔记弹窗以轻量调整为主，避免为了三类批注而完全推翻用户已经认可的原生选区和笔记创建流程。
- 批注在原文中的视觉提示应兼顾可读性，不应让标记大面积遮挡正文；具体采用何种标记形式，需结合 Koodo 原生高亮机制和实际效果再确定。

尚未完成：

- 三类批注在 Koodo 阅读器中的统一入口和面板布局。
- 小批注、章节批注、大批注的完整 UI。
- 大批注参考资料与正文编辑区的最终交互。
- 章节标题样式及其他阅读界面改造的完整实现与验收。

## 6. 当前技术架构与开发约束

当前仓库的架构（依据仓库 `AGENTS.md`）：

| 层 | 主要位置 | 职责 |
|---|---|---|
| Electron 主进程 | `main.js` | 窗口、IPC、SQLite（better-sqlite3）、原生集成 |
| React 渲染进程 | `src/` | UI、Zustand 状态管理、书籍展示和阅读器 |
| Kookit 阅读引擎 | `kookit` 独立源码仓库；Koodo 中使用构建产物 | 书籍解析、阅读相关工具 |
| Go HTTP 服务 | `httpserver/` | 可选 KOReader / OPDS 集成 |

开发时必须遵守：

1. 代码修改前先阅读当前仓库的 `AGENTS.md`，并检查 GitHub/本地当前分支的真实代码，不得依赖旧对话猜测实现。
2. 涉及代码编写、修改或 Review 前，先读取 `AGENTS.md` 和仓库内的 `.agents/skills/karpathy-guidelines/SKILL.md`；如果当前 Agent 的全局技能列表未提供该技能，直接读取仓库文件，不得因此阻塞开发。
3. 先搜索现有实现并复用，不做无必要的大规模重构。
4. 所有数据库操作必须通过 `database-command` IPC；渲染进程不得直接操作 SQLite。
5. 不得读取 `src/assets/lib/` 下的混淆/压缩产物来理解源码，包括 `kookit-extra.min.mjs`、`kookit.min.js`、`kookit-extra-browser.min.js`；需要研究阅读引擎时，应查看 Kookit 源码仓库。
6. Zustand 使用 `src/store/useAppStore.ts`，组件使用字段级 selector，不新增旧 Redux/connect 模式。
7. 用户可见文本使用 react-i18next，不硬编码界面文案。
8. 高频 `mousemove` / `scroll` / `resize` 事件必须按仓库规范节流。
9. 保护现有书库、笔记、高亮和阅读数据；数据库结构调整前先说明迁移与回滚策略。
10. 默认不主动提交或推送代码；用户明确要求提交时再执行。文档更新按用户要求单独处理。
11. 每个相对独立的功能完成后，执行类型检查、构建和针对性测试；不反复验收已通过的功能。

### 7.4 常用命令

在 Koodo 仓库目录中：

```powershell
# 启动桌面开发模式：Vite + Electron
yarn.cmd dev

# 仅启动浏览器网页版开发服务器
yarn.cmd start

# TypeScript 检查
yarn.cmd typecheck

# 前端生产构建
yarn.cmd build

# 单元测试
yarn.cmd test

# 单独启动 Electron（通常要求 Vite 服务已经运行）
yarn.cmd ele
```

**开发桌面版优先使用 `yarn.cmd dev`。** `yarn.cmd start` 只启动网页版 Vite 服务，不会自动打开 Electron 桌面窗口。此前单独执行 `yarn.cmd ele` 时，由于 Vite 服务没有运行，曾出现白屏；不要把它误判为桌面程序本身损坏。

在 Kookit 仓库目录中：

```powershell
yarn.cmd install --frozen-lockfile
yarn.cmd build
```

Kookit 的构建输出路径已调整为指向本地 Koodo Fork 的对应资源目录。修改 Kookit 源码后，需要重新构建，并确认 Koodo 使用的是最新构建产物。

### 7.5 Electron 安装的特殊情况

首次安装时 Electron 二进制下载曾因网络超时失败，但缓存中的 `electron-v35.7.5-win32-x64.zip` 已验证有效，已手动解压到 `node_modules/electron/dist`，并补齐 `path.txt` 和版本文件。执行 `electron.exe --version` 已返回 `v35.7.5`。

当前环境已经可以运行，不要无故删除 `node_modules` 或重复安装 Electron；如果以后确实需要重装，先检查本机 Electron 缓存，避免再次触发网络下载失败。

## 10. 下一阶段开发顺序

建议按以下顺序推进，避免性能问题与批注系统同时大改、难以定位回归原因：

1. **诊断验收**：先在当前 Electron 开发版打开约 70MB TXT，检查日志、内存采样和阅读耗时记录是否正常。
2. **性能基线**：记录首次打开、正文绘制、章节目录、连续滚动、选区和笔记操作表现。
3. **性能优化**：根据证据逐项处理最主要的瓶颈，每次改动都做针对性回归。
4. **章节与锚点基础**：检查 Koodo 现有章节信息和文本定位能力，确定稳定的原文锚点契约。
5. **三类批注数据模型**：先明确原生数据兼容策略，再设计并实现新模型。
6. **批注交互和界面**：优先复用原生选区、菜单、笔记弹窗，再逐步扩展章节批注和大批注。
7. **统一验收**：主要功能和界面完成后，再进行完整回归，不要反复要求用户重测已经通过的环境和数据互通项目。
