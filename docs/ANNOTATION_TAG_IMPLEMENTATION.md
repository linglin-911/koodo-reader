# UI-1：标签作用域基础与验证

更新：2026-11-09。本文记录UI-1数据阶段；后续UI-2～UI-6及UI-7自动验证见[UI实施记录](ANNOTATION_UI_IMPLEMENTATION.md)。**正式书库迁移与实书人工验收仍未执行。** UI-1未新增全局标签管理界面。

## 1. 数据与迁移

- 沿用原 `notes.db`，将独立 `annotation_schema` 从 v1 追加升级为 v2；不改变 TXT 索引/恢复版本域，不创建第二套数据库或正文实体。
- 新表 `annotation_tags(id,name,scope,book_key,version)` 保存身份；`scope=global` 跨书使用，`scope=book` 只属于指定书籍。同名全局/局部、不同书同名局部均独立。全局兼容 ID 由原名称确定，局部使用 UUID；名称按精确文本比较，不自动合并大小写、空白或 Unicode 不同的历史名称。
- `note_tags(note_key,tag_id,position)` 是唯一权威引用，复合主键去重，外键和触发器阻止跨书局部引用；`note_tags_tag(tag_id,note_key)` 支持计数/反查。三类实体都通过同一关系表引用标签。
- `notes.tag` 保留为旧客户端的名称 JSON 投影；同名不同身份可在这个兼容字段中只显示一个名称，但权威引用、`tagRefs` 与 v2 备份不会塌缩。UI-1 不删除历史 `title`、颜色/样式、空正文小批注或解绑快照。
- 迁移前用 SQLite 一致备份生成 `notes.db.pre-annotations-v2-<uuid>.bak`；DDL、引用导入与版本提升在同一事务，失败回滚，重新连接/重跑幂等。迁移仅按键读取每页最多200条 `key,tag`，不把完整批注正文读进迁移 JS 数组。原正式实体字段、版本、时间、绑定、绘图及索引内容保持。
- 旧 JSON 名称没有局部归属证据，按原跨书语义导入为全局兼容标签，不根据人物名推断局部。旧 `ConfigService.noteTags` 中未被使用的名称也会通过受控初始化保留；新建/保存前首次初始化按书库合并请求，失败可重试。

核心实现：`src/utils/main/annotation-tags.js`、`annotation-store.js`；前端接口位于 `src/utils/storage/annotationService.ts`。始终通过 `database-command` 的受控 annotations action 访问。

## 2. 服务契约与并发保护

| action / API | 行为 |
|---|---|
| `tag-list` / `AnnotationTagService.list` | 可选全局或指定书籍局部范围；默认页100、上限200；返回稳定身份、版本、使用批注数量及 hasMore。选择场景可返回全局+本书局部 |
| `tag-create` / `.create` | 建立全局或指定书籍局部身份；同作用域精确同名返回原身份。这里只提供基础能力，不增加全局管理入口 |
| `tag-rename` / `.rename` | 仅允许本书局部标签。无冲突原子重命名；同名先返回 requiresMerge、源/目标数量与去重影响实体数，不写数据。确认时传源版本、目标ID及版本才合并 |
| `tag-delete` / `.delete` | 仅允许本书局部标签。有使用时先返回 requiresConfirmation 和影响数量；确认后删除标签和引用，不删除正文/实体/其他标签/原文绑定。未使用标签可直接删 |
| `tag-seed-legacy` | 兼容初始化旧配置中的名称；幂等保留未使用的全局兼容身份，不改批注正文 |
| `AnnotationService.create/save` | 新客户端可传 `tagIds`，按身份保存；读取额外返回 `tagRefs`。旧客户端继续用 `tag:string[]`，可修改全局名称引用，保留它无法可靠区分的局部身份 |
| `AnnotationService.list({tagIds})` | 按身份筛选；旧 `tags` 名称筛选继续兼容，但新作用域控件应使用 ID |

使用数量按独立批注实体计数，包含无绑定实体，不按小批注位置数计算。追加/移除引用或删除实体时同步推进相关标签版本，过期的删除/合并确认会被拒绝。重命名、合并、删除同步更新受影响实体的名称投影及版本，阻止旧编辑窗口把被删/被合并关系写回来。

正文保存、标签身份解析和引用替换在同事务；选文原子创建仍包含实体+标签引用+原文绑定。关联写入、合并/删除中途或导入中途发生 SQL 故障时，所有相关写入一并回滚。历史按名称 `remove-tag` 只解除对应旧全局引用，不能误命中同名局部标签；全局身份的完整管理仍暂缓。

## 3. 备份、恢复与快照

- 新清单为 `annotations.v2.json`，包含原正式实体、三类绑定/快照/样式、绘图，以及标签身份和带顺序的关系。普通 ZIP、快照和数据库单独导出都保留作用域；共享文件名配置已显式加入 Electron 打包清单，并验证 ASAR 中可加载。
- v1正式 JSON 清单和 v1正式数据库仍可导入：名称转为稳定全局引用；只读打开旧数据库，不就地改写备份。v2往返保留同名不同作用域、未使用标签和身份。相同数据重复导入幂等，已有兼容全局身份可复用；自然同名但不同局部 ID、已改名身份或较新实体/引用发生冲突则整笔拒绝，不自动覆盖或猜测合并。
- 同时存在 v1/v2 时只使用 v2；v2损坏、文件名与内容版本不符、未来未知版本均失败，不回退到旧清单或 `notes.db`，避免丢失作用域。
- 修正旧快照入口直接覆盖 `notes.db` 的行为：正式批注统一经版本化导入/冲突检查。旧快照不能覆盖新正文或悄悄撤销标签变更。三条恢复入口均保留当前目标 `storageLocation`，不因备份来自其他路径而把后续导入转向原书库。
- 全包恢复的其他库/配置/资产仍沿用既有流程，**不是整个书库的跨库原子事务**；上述原子性针对正式批注及标签事务。没有据此宣称硬断电、多库合并或新版云同步已验收。

对应适配：`src/utils/file/backup.ts`、`restore.ts`、`src/utils/main/backup-util.js`、`src/utils/storage/annotationBackup.ts`。旧云 notes.db 同步仍保护性停用。

## 5. 本阶段边界与下一步

UI-1只完成作用域数据、受控服务、兼容和备份。当前旧编辑器仍显示原有名称控件；全局/局部选择器将在UI-2快速记录流程中接入，局部管理UI在UI-6实现。没有增加标题、内部分类、标签颜色、全局管理页面或自动保存设计，也没有修改 Kookit/阅读窗口/目录算法。

下一阶段为UI-2；后续继续按专项需求拆分阅读快速记录、当前章查询和统一管理职责。正式库迁移及实书人工验收保留待测，旧阶段11约8.5秒发布事务等遗留项保持原状态。
